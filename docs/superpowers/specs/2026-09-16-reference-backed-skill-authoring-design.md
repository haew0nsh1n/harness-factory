# Reference-backed skill authoring

Date: 2026-09-16

Status: 방향 승인 완료. 상세 설계 검토 대기. 구현 및 배포 승인과는 별개다.

## 1. 목표와 결정

기존 `hf-*` 스킬의 실행 품질을 높이고, 고객 인터뷰에서 드러난 새로운
역량을 검토된 외부 스킬 패턴에 근거하여 동적으로 작성한다.
사용자는 **설계 시점 생성·검증, 실행 시점 버전 고정** 방향에 동의했다.

SOTA는 참조 후보를 지칭하며 성능 인증이 아니다. 유명 저장소의 이름이나
문서 길이로 품질을 판정하지 않고, 동일 시나리오의 관찰 결과로 평가한다.

- 기존 스킬로 충족하면 재사용한다. 맥락 차이는 특화하고, 실제 역량 공백만 신규 생성한다.
- 생성 후보는 실행 가능한 승인 자산과 분리한다. LLM은 검증 상태나 승인을 발급하지 않는다.
- 생성·평가에는 서버가 검토한 고정 참조만 제공한다. 고객 실행 및 빌드에는 검색이나 LLM 호출이 없다.
- 고객 정책은 별도 정책 스킬로 유지한다. 원본 스킬의 지시가 정책·권한·승인을 덮어쓰지 못한다.
- 기존 설치·레지스트리와 패키지 수준 행동 평가·고객 환경 사전 점검은 유지한다.

대안은 기존 문구만 보강하거나, 매번 원본 최신 버전을 검색하여 생성하는 것이다.
전자는 신규 역량 공백을 해결하지 못하고 후자는 재현성과 변경 검토를 어렵게 하므로 채택하지 않는다.

## 2. 현재 구조와 변경 이유

- [카탈로그](../../../catalog/catalog.json)는 단일 upstream 출처와 리비전을 기록한다.
  여섯 스킬은 각 31~43줄이며 별도 참조 문서가 없다.
- [패키지 생성기](../../../harness_factory/package.py)는 카탈로그의 선택된 디렉터리를
  복사한다. 새로운 업무 스킬의 본문을 작성하지 않는다.
- [인터뷰 프롬프트](../../../web/api/interviews/prompts.py)와
  [참조 검증기](../../../web/api/interviews/catalog.py)는 서버 카탈로그에 있는 ID만 허용한다.
  이 보안 경계는 제거하지 않고, 검증된 설계별 카탈로그로 확장한다.
- [카탈로그 계약](../../../harness_factory/contracts.py)은 v1의 정확한 필드,
  단일 MIT 출처, 선택 스킬의 `verified` 상태를 요구한다.
  행동 증거는 현재 `SKILL.md` 해시에 연결되어 있어, 새 참조 문서까지 연결하도록 확장해야 한다.
- [설계 digest](../../../web/api/designs/digest.py)는 JSON 문서를 묶지만 스킬 리소스
  바이트를 직접 포함하지 않는다. 새 스냅샷에는 전체 리소스 해시 목록이 필요하다.
- [설계 서비스](../../../web/api/designs/service.py)와
  [빌드 서비스](../../../web/api/builds/service.py)는 현재 서버 카탈로그와 설계 카탈로그를
  비교한다. 새 설계는 승인 당시의 불변 스냅샷을 검증해야 한다.
- [기존 행동 평가](../../evaluations/2026-09-10-copilot-skills.md)는 제한된
  시뮬레이션이다. 과거 결과를 새 본문이나 새 참조 문서의 검증 결과로 재사용할 수 없다.

## 3. 범위와 구현 단위

하나의 거대한 변경 대신 아래 순서로 구현하고 각 단위에 별도 구현 계획을 작성한다.

1. **기반 및 기존 스킬:** 참조·번들·평가 계약, 고정 참조 라이브러리, 여섯 스킬 보강,
   전체 리소스 무결성, baseline 비교. 신규 생성 없이도 품질을 검증할 수 있는 단위다.
2. **설계 시점 생성:** 역량 매칭, 특화/생성 후보, 격리된 평가, 테넌트별 후보 저장,
   검증된 설계별 카탈로그와 digest 승인·빌드 연결. 첫 수직 경로는 신규 read/local 스킬이다.
3. **Studio 연결:** 생성 후보·근거·평가·차이 검토 UI와 인터뷰에서 승인·빌드까지의 수용 테스트.

새 벡터 DB, 별도 마이크로서비스, 범용 에이전트 프레임워크는 도입하지 않는다.
기존 FastAPI/DB/모델 호출 경계와 lease·revision·idempotency 패턴을 재사용한다.
외부 커넥터 생성, 런타임 자기 수정, 자동 upstream 업데이트, 전역 카탈로그 자동 승격,
고객 저장소의 실작업 자동 실행은 범위 밖이다.

## 4. 데이터 흐름과 책임

```text
검토한 upstream snapshot → 역량별 참조 라이브러리
                                     ↓
확인된 인터뷰 요구 → 재사용/특화/생성 결정 → 후보 bundle
                                            ↓
                            정적 검사 → 행동 평가 → 검토
                                            ↓
                          불변 설계별 effective catalog
                                            ↓
                     workflow·scenarios 확정 → digest 승인
                                            ↓
                    오프라인 빌드 → 패키지 평가 → 배포·설치
```

- 참조 수집은 유지관리자가 승인한 공개 저장소의 고정 커밋만 대상으로 한다.
  고객 인터뷰나 소스 코드를 공개 검색·원본 저장소로 전송하지 않는다.
- 매처는 입력/출력 의미, 작업 목적, 필요한 도구, 허용 effect, runtime을 비교한다.
  첫 버전은 태그 기반 후보 축소와 구조화된 모델 제안을 사용한다. 브랜드명 매칭은 하지 않는다.
- 작성기는 요구사항과 선택된 참조 패턴으로 후보 문서만 생성한다.
- 평가기는 실제 후보 바이트를 읽고 합성 입력·mock 도구 결과로 행동을 관찰한다.
- 카탈로그 resolver만 검증된 bundle을 설계에 결합할 수 있다.
  작성기나 인터뷰 모델은 카탈로그 파일·증거·승인 레코드를 수정할 수 없다.
- 빌더는 승인된 스냅샷을 읽고 바이트를 검증·복사할 뿐 생성하지 않는다.

## 5. 고정 참조 라이브러리

초기 참조는 현재 카탈로그에 기록된 커밋을 출발점으로 삼는다.
이를 최신 버전이나 최적 버전이라고 주장하지 않는다. 변경은 별도 검토 대상이다.

| Repository | Revision | 초기 참조 경로 |
| --- | --- | --- |
| `https://github.com/obra/superpowers` | `b36e0829c6d0140e93cfef2ca599b1b07d4a7797` | `skills/writing-plans/SKILL.md`, `skills/test-driven-development/SKILL.md` |
| `https://github.com/mattpocock/skills` | `3cca18b368ae95cdbdebbff572ccafa662551015` | `skills/productivity/grilling/SKILL.md`, `skills/engineering/wizard/SKILL.md` |
| `https://github.com/garrytan/gstack` | `71f6048e8ada25180e61438abc1d98cb151fe9a7` | `review/SKILL.md` 및 검토에 필요한 로컬 참조 |

이 설계 조사에서는 고정 커밋의 writing-plans, grilling, review 원문을 확인했다.
나머지 경로 및 전이 참조의 수집·라이선스·무결성 확인은 구현 시 별도 완료 조건이다.

각 참조 레코드는 ID, repository, revision, path, 내용 SHA-256, 라이선스 파일과 해시,
역량 태그, 원본 내 section, 채택한 방법, 제외한 동작, 검토자와 검토 상태를 가진다.
본문과 참조 파일을 로컬 snapshot으로 보관하고 정확한 바이트를 검토한다.
변형한 패턴에는 자체 digest와 원본 연결을 함께 기록한다.

허용 저장소·경로·크기 제한을 적용하고 symlink, 경로 탈출, 실행 파일 및 hooks를 거부한다.
원본의 상대 참조는 허용 루트 내에서만 해석하고 미수집 참조는 명시적으로 제외한다.
첫 버전은 기존 정책과 같은 MIT 출처만 수용한다. 미확인 라이선스는 차단하고
실제로 사용한 출처의 notice를 배포 번들에 포함한다.

원본에 있는 설치, 자동 커밋, telemetry, 외부 리뷰 서비스, 사용자 홈 경로 및
강제 서브에이전트 호출 지시는 자동 실행하거나 그대로 이식하지 않는다.
공통 라이브러리에는 고객 정보가 없고, 고객별 파생 bundle은 공유 캐시에 저장하지 않는다.

## 6. 기존 스킬 보강 기준

각 스킬은 짧은 진입 문서와 필요할 때만 읽는 `references/`, `templates/`로 나눈다.
필수 구성은 적용·비적용 조건, 입력 전제, 실행 단계와 분기, 산출물 계약,
중단·복구·재개, 권한 경계, 예시, 검증 기준, adaptation 근거다.
단순 섹션 존재 검사는 품질 평가를 대신하지 않는다.

| Skill | 보강할 실제 판단 능력 |
| --- | --- |
| `hf-clarify` | 결정의 선행조건, 확인 가능한 사실과 사용자 결정 구분, 모순 해결, 질문 종료 기준, brief 예시 |
| `hf-plan` | 실제 파일·인터페이스 확인, 독립 검증 가능한 작업 분해, 실패/성공 테스트 명령, 산출물 인계 템플릿 |
| `hf-tdd` | assertion 실패와 환경 오류 구분, 이미 있는 구현 처리, 회귀 범위, flaky/실행 불가 상황, 관찰 기록 |
| `hf-review` | 변경 유형별 점검, enum 변경의 호출자 추적, 데이터·동시성·신뢰 경계, 근거 없는 지적 억제 |
| `hf-manual` | 담당자·승인·절차·완료 증거, 불확실한 외부 쓰기의 재시도 금지, 재개 판단 |
| `hf-issues-markdown` | 필드·상태 검증, 사용자 작성 영역 보존, 충돌·중복·잘못된 입력 대응, Git 게시 경계 |

모든 스킬에 모든 패턴을 넣지 않는다. 예를 들어 문서 작성에 TDD 실행을 강제하지 않는다.
확인하지 않은 파일·명령을 구체적으로 꾸며내는 것보다 누락 전제를 표시하도록 한다.

## 7. 생성 후보와 계약

요구 레코드에는 목적, 확인된 evidence ID, 입력/출력, 효과, 도구, 승인 조건,
관찰 가능한 성공 기준을 담는다. 모델이 제안한 정보는 확인된 사실로 자동 승격하지 않는다.

- **재사용:** 기존 계약과 방법이 충분하면 원본 bundle digest를 그대로 참조한다.
- **특화:** 방법론은 동일하고 업무 절차가 달라지면 고객 범위의 새 bundle을 만든다.
  단순 용어·정책 차이는 가능한 한 별도 customer-rules로 해결한다.
- **신규 생성:** 기존 계약으로 충족하지 못하는 이유를 기록하고 관련 참조에 근거해 작성한다.
  적합한 참조가 없으면 `missing-reference`로 차단하거나 고객이 검토할 수동 인계를 제안한다.

신규 스킬은 첫 버전에서 `read`, `local`, `manual` effect만 허용한다.
기존에 검증된 외부 도구 스킬의 사용은 유지하지만 생성기가 새 external-write 경로를
발명할 수 없다. 도구 binding은 확인된 profile capability의 부분집합이어야 한다.
ID는 서버가 유효한 kebab-case로 발급하고 `customer-rules`, workflow ID 및 선택 스킬과의
충돌을 거부한다. 모델은 경로나 파일명을 통한 루트 탈출도 할 수 없다.

생성 모델의 출력은 제한된 Markdown 파일 집합과 구조화된 제안이다.
임의 스크립트·바이너리·네트워크 URL 실행·frontmatter 도구 권한 추가는 허용하지 않는다.
프롬프트 경계와 문자열 검사는 보조 수단이다. 실제 차단은 서버 권한 및 격리 환경에서 수행한다.

### 상태와 소유권

내용 버전의 상태는 `candidate → checked → evaluated → accepted`다.
실패는 `rejected`, 실행 불가는 `blocked`로 기록한다. 상태 전이는 서버가 검증하며,
`evaluated`는 통과 결과가 있을 때만 가능하다. `accepted`는 권한 있는 reviewer의 명시적 판단이다.
이 판단은 workflow digest 승인, 게시 승인, 설치 승인 및 작업 실행 권한을 대신하지 않는다.

내용 수정은 항상 새로운 버전으로 만들며 과거 평가·승인을 승계하지 않는다.
작업의 running/succeeded/failed 상태는 내용 버전의 상태와 분리한다.
작업은 request ID, 입력 digest, 기준 revision, lease token을 사용한다.
동일 요청의 재전송은 저장된 결과를 반환하며 stale revision의 결과는 채택하지 않는다.
실패 후 재시도는 새 시도 ID로 남기고 모델 타임아웃을 성공으로 취급하지 않는다.

## 8. 불변 bundle, 카탈로그 및 승인

v1의 단일 upstream 필드를 가짜 Git 커밋으로 채우지 않는다. 새 계약은 명시적 v2다.

- Bundle manifest: schema version, skill ID, runtime, 입력/출력/requires/effects,
  정렬된 상대 경로별 SHA-256과 크기, 출처 목록, adaptation 목록을 포함한다.
- Upstream 출처는 실제 repository/revision/path와 notice를 가진다.
  생성 출처는 생성 run ID, 요구사항 digest, 참조 bundle digest 목록,
  모델/deployment 식별자, 반환된 모델 버전 정보, prompt version과 매개변수를 기록한다.
  공급자가 주지 않은 모델 버전은 unknown으로 남긴다. 출처는 재현 단서이지 결정론 보장이 아니다.
- Bundle digest는 digest 자신을 제외한 canonical manifest의 SHA-256이다.
  모든 실행 지침·template·notice가 파일 목록에 포함되고 누락/추가 파일을 거부한다.
- 평가 보고서·승인 기록은 bundle 외부에서 digest를 참조한다. 자기 참조 해시 순환을 만들지 않는다.
- Effective catalog는 immutable base snapshot과 해당 고객·설계 범위의 accepted bundle을 결합한다.
  ID 충돌은 거부하고 암묵적인 shadowing은 허용하지 않는다.
- v2 design digest에는 기존 네 문서 외에 effective catalog snapshot과 선택된 bundle digest,
  시나리오·평가 정책·보고서 digest를 묶는 lock을 포함한다. 조회 가능한 승인 근거가 바뀌면 재승인한다.
- build와 package check는 동일 lock을 검증하고 저장된 bundle만 materialize한다.
  승인 후 전역 카탈로그가 바뀌어도 기존 설계를 조용히 다른 버전으로 빌드하지 않는다.

Resolver와 bundle 조회·저장·승인 모두 organization/customer/design 범위를 검사한다.
해시를 안다는 것만으로 다른 고객 bundle에 접근할 수 없다. DB의 참조에도 테넌트 경계를 적용한다.
삭제·보존 정책은 승인 자산의 참조 무결성을 보존하며, 거절된 후보와 원시 고객 입력의 접근을 제한한다.

v1 패키지·게시 자산은 기존 해시와 계약을 그대로 유지한다.
v1-only CLI는 v2를 명확한 unsupported-version 오류로 거부해야 한다.
v2 지원 reader/installer를 먼저 제공하고 새 설계 경로를 활성화한다.
레거시 증거를 새 bundle 검증으로 자동 변환하지 않는다.

## 9. 평가와 품질 게이트

### 정적 검사

Frontmatter, 계약, 전체 파일 해시, 로컬 참조, 도구/effect, 승인 조건, 라이선스,
경로·크기 제한을 검사한다. 정적 통과는 `checked`이지 `verified`가 아니다.

### 행동 평가

검토된 테스트 세트로 기존 스킬과 후보를 같은 조건에서 평가한다.
최소한 정상 수행, 모호한 입력, 승인 거절, 도구/접근 부재, 실패 결과,
중단·재개, 불확실한 외부 쓰기, instruction injection을 포함한다.
리뷰는 의도적으로 심은 결함의 발견과 오탐을, clarify는 불필요한 질문과 미확인 가정을,
plan/TDD는 구체적인 테스트·산출물과 실패 결과의 정직한 처리를 평가한다.

평가 실행기는 생성기와 별도의 호출 문맥을 사용한다. 실제 bundle과 합성 입력만 제공하고
기대 정답·채점 rubric은 평가 대상 에이전트에게 주지 않는다.
실제 고객 자격증명·쓰기 도구·브라우저 세션·고객 시스템 접근은 제공하지 않는다.
모델 API 접속은 서버의 허용된 채널로만 수행하며 평가 대상에게 네트워크 도구를 주지 않는다.

원시 응답, 관찰된 결정과 금지 행동, scenario digest, bundle digest, 모델 정보,
prompt/rubric version, 시도 ID를 보존한다. Deterministic 검사는 서버에서 수행하고,
판단이 필요한 품질 항목은 reviewer가 원시 응답을 확인한다. 생성기의 자기 점수는 증거가 아니다.

통과 조건은 모든 필수 시나리오와 안전 조건의 충족이다. 품질 점수는 임의의 종합 점수 대신
각 시나리오의 사전 정의된 관찰 항목 충족 여부로 기록한다.
기존 스킬 교체는 동일 baseline 대비 필수 항목 퇴행이 없고,
사전에 지정한 보강 항목에서 최소 하나의 관찰 가능한 개선이 있어야 한다.
신규 스킬은 별도 검토된 역량별 수용 항목을 모두 충족해야 한다.

개발 중 공개한 실패 사례와 별도로 held-out 사례를 유지한다.
보정은 최대 두 번까지만 허용하며, 보정마다 새 버전과 새 평가를 남긴다.
한 번이라도 관찰된 위험 행동을 보고서에서 지우지 않는다.
최종 승격에는 최종 바이트에 대한 새 전체 평가가 필요하다.
평가 기능이 없거나 결과가 불완전하면 `blocked`로 남긴다.

이 평가는 bounded simulation이며 실환경 구현 성공이나 쓰기 권한 인증이 아니다.
기존 패키지의 `evaluate`는 관찰 결과를 봉인하는 역할을 유지하고,
새 평가 실행기를 호출하는 기능과 혼동하지 않는다.
패키지 조합 전체 평가와 고객 환경 preflight는 스킬 단위 평가 후에도 별도로 필요하다.

## 10. 인터뷰와 Studio 통합

인터뷰 모델이 새 스킬 ID를 즉시 workflow에 삽입하도록 제한을 풀지 않는다.
확인된 요구사항에서 역량 공백을 먼저 제안하고, 작성·평가·검토 후 effective catalog를
만든 다음 기존의 엄격한 workflow 작성 및 참조 무결성 검사를 수행한다.
후보 처리 중에는 설계 준비 상태만 표시하며 승인 가능한 workflow인 것처럼 보여주지 않는다.

기존 Studio 설계 화면에 다음을 추가한다.

- 각 단계의 재사용/특화/신규 생성 구분과 선택 이유.
- 참조 원본·고정 버전·채택/제외 이유, 실제 스킬 본문과 리소스 diff.
- 구조 검사, 행동 평가, 사람 검토, 설계 승인 상태의 분리 표시.
- 확인된 요구사항과 생성 결과의 연결, 실패 사례와 미확인 사항.
- 명시적 생성 요청, 평가 실행, 후보 수락/거절, 변경 후 재승인 동작.

초기화·실패·타임아웃·stale revision·평가 불가 상태를 한국어로 표시한다.
새 화면을 별도 제품으로 만들지 않고 기존 설계·승인 흐름을 확장한다.
LLM 호출은 API 경계 안에 두고 오프라인 builder의 egress 제한을 유지한다.

## 11. 검증 및 완료 기준

구현 계획은 각 단위의 실패 테스트부터 작성한다. 최소 검증 범위는 다음과 같다.

1. 참조 선택의 적합/부적합, 누락 참조, 허위 출처·license·revision 거부.
2. 재사용/특화/생성 판단, ID 충돌, 허용하지 않은 effect와 tool binding 거부.
3. `SKILL.md`를 바꾸지 않고 reference/template만 바꿔도 평가·승인·빌드 무결성 검사 실패.
4. 후보/blocked/rejected bundle의 카탈로그 편입 및 빌드 거부.
5. 재시도 멱등성, stale completion, 동시 변경, 교차 테넌트 bundle 접근·승인 거부.
6. 승인 후 upstream 또는 전역 카탈로그 변경 시 기존 lock 유지와 새 설계의 재승인.
7. v1 패키지 회귀, v2 설치, 변조 탐지, builder 네트워크·LLM 미호출.
8. 여섯 기존 스킬의 비교 평가와 최소 한 개 실제 생성 후보의 독립적인 행동 평가.
9. 인터뷰 요구 → 신규 후보 → 평가 → 검토 → workflow 승인 → 빌드 → 패키지 평가의 수용 테스트.

Mock/unit 테스트 성공을 실제 에이전트 평가 성공으로 표시하지 않는다.
새 스킬 증거를 얻기 전에는 기존 verified 본문·보고서를 덮어쓰지 않고 후보 영역에서 작업한다.
기존 스킬 배포 교체는 새 증거와 함께 수행한다. 단순히 해시만 고쳐 과거 통과를 유지하지 않는다.

## 12. 다음 단계

이 문서 검토 후 첫 단위인 **참조·bundle·평가 기반과 기존 스킬 보강**의 구현 계획을 작성한다.
그 계획에서 변경 파일, 마이그레이션, 테스트 명령과 실제 평가 실행 수단을 확정한다.
후속 단위는 이 설계의 계약을 유지하되 각각 구현 전에 상세 계획을 작성한다.
이 문서 작성만으로 구현·평가·게시가 완료되었다고 주장하지 않는다.
