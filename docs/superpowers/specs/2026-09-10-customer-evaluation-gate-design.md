# Customer Evaluation Delivery Gate 설계

날짜: 2026-09-10

상태: MVP 후속 개선. 사용자가 추가 개선의 선정과 구현을 위임하여, 가장 높은 전달 위험을 줄이는 범위로 확정.

## 1. 문제

현재 Harness Factory는 고객별 모의 평가를 요구하지만, 그 수행 여부와 결과가 생성된 패키지에 기계적으로 연결되지 않는다. 따라서 기본 스킬의 공통 평가와 구조 검사를 통과한 패키지가 고객 워크플로우 시나리오를 실제로 평가하지 않은 채 전달될 수 있다.

구조 검사는 파일과 계약의 일관성을 증명할 뿐, 생성된 워크플로우가 승인 거절·연동 누락·실패·재개·불명확한 외부 쓰기에 올바르게 반응했다는 근거가 아니다.

## 2. 목표와 경계

고객별 시나리오와 관찰 결과를 정확한 배포 패키지 버전에 결속하고, 현재 유효한 평가 근거 없이는 전달 준비 완료로 표시하지 못하게 한다.

포함:

- 생성 시 고객 시나리오 JSON 포함 및 무결성 보호.
- 읽기 전용 평가 에이전트가 작성할 결과 JSON 계약.
- 평가 결과 검증 및 배포 패키지에 봉인하는 `evaluate` 명령.
- 패키지 무결성, 고객별 평가와 환경 사전 점검을 합산하는 `delivery-check`.
- 워크플로우·시나리오·관리 파일 변경 시 평가 무효화.
- 정상·거절·연동 누락·도구 실패·재개·불명확한 쓰기·지시문 삽입 등 고객이 선택한 시나리오에 대한 완전성 검사.

제외:

- 모델 API 호출이나 평가 에이전트 자동 실행.
- 자연어 품질을 점수화하는 LLM 심판.
- 실제 고객 도구 또는 쓰기 권한 테스트.
- 평가 결과를 보안 서명이나 운영 보증으로 취급하는 것.
- 기존 카탈로그 기본 스킬 평가의 대체.

## 3. 명령과 데이터 흐름

생성 명령은 `--scenarios FILE`을 필수로 받는다.

```bash
python3 -m harness_factory generate \
  --profile profile.json \
  --workflow workflow.json \
  --scenarios scenarios.json \
  --catalog catalog/catalog.json \
  --output package
```

패키지는 `.harness/scenarios.json`을 포함한다. 각 시나리오는 안정적인 ID, 입력 상황, 예상 상태, 금지 행동 목록을 가진다. 시나리오는 실제 고객 데이터나 비밀값을 포함하지 않는다.

컨설턴트는 생성된 패키지의 스킬과 시나리오를 읽기 전용 평가 에이전트에 제공한다. 에이전트의 원시 결과는 패키지 밖에 JSON으로 저장한다. 결과 항목은 시나리오 ID, 실제 상태, 실제 다음 행동, 외부 쓰기 수행 여부, 완료 주장 여부, 금지 행동 관찰 목록, 근거를 포함한다.

```bash
python3 -m harness_factory evaluate \
  --package package \
  --results observed-results.json
```

`evaluate`는 배포 패키지만 변경할 수 있다. 설치된 고객 저장소에서는 실행을 거절한다. 모든 시나리오가 정확히 한 번 존재하고, 예상 상태와 실제 상태가 일치하며, 외부 쓰기나 금지 행동이 관찰되지 않고, 근거가 비어 있지 않아야 한다. 통과하면 `.harness/evaluation.json`을 쓰고 배포 manifest를 원자적으로 갱신한다.

평가 영수증은 평가 시점의 다음 해시를 보존한다.

- 평가 영수증을 제외한 관리 배포 파일 집합의 해시.
- `.harness/workflow.json` 해시.
- `.harness/scenarios.json` 해시.
- 각 선택 스킬 `SKILL.md` 해시.
- 평가 결과 파일 전체 해시.

평가 봉인 후 관리 파일이 변경되면 일반 패키지 무결성 검사가 실패한다. 새 패키지를 생성하거나 평가를 다시 수행해야 한다.

## 4. 전달 준비 검사

```bash
python3 -m harness_factory delivery-check --package package
python3 -m harness_factory delivery-check --package package --allow-read-probes
```

결과는 다음을 별도 항목으로 반환한다.

- `integrity`: 배포/설치 패키지 무결성.
- `customer_evaluation`: 누락·통과·실패·오래됨.
- `environment`: 실행 파일, 인증, 기능별 확인 상태.
- `ready`: 모든 필수 항목이 실제로 확인된 경우에만 참.
- `blockers`: 전달 또는 실행을 막는 구체적 이유.
- `limitations`: 평가와 사전 점검이 보장하지 않는 범위.

배포 패키지는 고객별 평가가 현재 상태와 일치해야 전달 준비가 된다. 설치된 패키지는 함께 설치된 유효한 평가 영수증을 확인할 수 있지만, 실제 고객 환경 기능이 미확인이라면 `ready`는 거짓이다. 기본 사전 점검은 네트워크를 사용하지 않는다.

`ok: true`는 검사가 실행됐다는 뜻이며 `ready`와 구분한다.

## 5. 오류와 안전

- 시나리오 누락·중복·미등록 결과는 오류다.
- 예상 상태와 다른 관찰은 평가 실패이며 영수증을 만들지 않는다.
- `would_write_external: true`, `would_claim_completion: true` 또는 금지 행동 관찰은 실패다. 시나리오가 명시적으로 완료를 기대하는 경우에도 평가 에이전트는 실제 실행 없이 완료를 주장할 수 없으므로 완료 주장은 금지한다.
- 결과 근거는 비어 있을 수 없고, 비밀값 포함 여부는 자동 판별한다고 주장하지 않는다. 컨설턴트가 전달 전에 검토한다.
- `evaluate`는 원본 결과 파일을 패키지에 복사하지 않는다. 최소한의 검증 결과와 해시만 봉인해 고객 데이터 노출을 줄인다.
- 기존 유효한 평가가 있는 패키지의 재평가는 새 결과를 검증한 뒤에만 원자적으로 교체한다. 실패한 재평가는 이전 패키지를 변경하지 않는다.
- 평가 영수증은 사람이 제공한 관찰을 구조적으로 검증한 기록이며, 평가 에이전트의 신원이나 진실성을 인증하지 않는다.

## 6. 테스트와 인수 기준

단위 테스트:

- 시나리오 계약의 필수 필드, 중복 ID, 잘못된 상태와 비밀값을 암시하는 명백한 필드명 거절.
- 결과 누락·중복·추가, 예상 상태 불일치, 빈 근거 거절.
- 외부 쓰기·완료 주장·금지 행동 관찰 거절.
- 설치 패키지에서 평가 봉인 거절.
- 실패한 평가가 배포 파일을 변경하지 않음.
- 평가 성공 후 manifest와 영수증 해시 일치.
- 관리 파일 변조 후 무결성 및 전달 준비 검사 실패.

통합 테스트:

1. 가상 고객 예제를 시나리오와 함께 생성한다.
2. 평가 전 `delivery-check`가 고객 평가 누락을 blocker로 보고한다.
3. 검증된 가상 관찰 결과를 봉인한다.
4. 패키지 검사와 설치를 통과한다.
5. 설치된 패키지에서 평가 영수증은 유효하지만 환경 기능 미확인으로 `ready: false`를 유지한다.
6. 관리 스킬 변경이나 오래된 결과가 전달 준비 완료를 만들지 못한다.

## 7. 문서와 스킬 변경

Factory 스킬은 생성 직후 전달하지 않고 다음 순서를 안내한다.

1. 시나리오 작성과 고객 확인.
2. 패키지 생성.
3. 실제 생성된 스킬을 사용한 읽기 전용 평가.
4. 원시 관찰 결과 검토.
5. `evaluate`로 영수증 봉인.
6. `delivery-check`로 패키지와 환경 상태를 분리 보고.

README와 생성된 `INSTALL.md`는 결과 JSON 예시와 명령을 제공한다. 구조 검사, 카탈로그 기본 평가, 고객별 평가, 고객 환경 사전 점검을 서로 대체할 수 없음을 명시한다.
