# Harness Factory 설계

날짜: 2026-09-10

상태: 설계 승인 후 사용자의 자율 구현 지시에 따라 MVP를 구현. 구현 계획과 인수 기록은 인접 문서를 참조.

## 1. 목표와 제품 경계

Harness Factory는 컨설턴트·엔지니어가 GitHub Copilot CLI에서 실행하는 스킬 기반 생성기다. 고객 인터뷰로 SDLC, 병목, 도구와 시스템 연동을 파악하고, 고객 환경에 설치할 실행 가능한 아우터 하네스 패키지를 만든다.

아우터 하네스는 코딩 에이전트를 대체하지 않는다. 기존 Copilot CLI의 바깥에서 워크플로우 단계, 스킬 선택, 컨텍스트와 산출물 전달, 승인, 검증 및 수동 인계를 안내한다.

첫 버전은 SDLC 전체를 진단하되, 고객이 승인한 우선 워크플로우 하나만 생성한다. 전달 이후 고객은 팩토리에 상시 연결하지 않고 자신의 Copilot CLI에서 하네스를 실행한다.

### 포함

- 컨설턴트가 고객과 대화하며 답변을 입력하는 적응형 인터뷰.
- 고객 프로필과 워크플로우 명세의 구조화 및 승인.
- 선별된 기본 스킬과 고객별 스킬의 조립.
- 기존 MCP 서버와 CLI에 대한 연동 요구사항 및 설정 예시.
- 프로젝트 스킬 패키지, 설치 안내, 출처 및 라이선스 정보.
- 패키지 구조 검증, 샘플 이슈 모의 실행, 고객 측 사전 점검.
- 로컬 실행 기록을 활용한 승인 대기, 수동 인계, 실패 및 재개 안내.

### 제외

- 웹 인터뷰 UI, 중앙 운영 대시보드, 상시 실행 서버.
- 새로운 코딩 에이전트 또는 강제 실행을 보장하는 워크플로우 엔진.
- GitHub Copilot CLI 외 런타임 지원.
- 신규 MCP 서버나 고객 API 커넥터 코드 자동 생성.
- 여러 독립 워크플로우의 동시 생성 및 조직 전체 스킬 마켓플레이스.
- 기본 스킬의 무승인 자동 업데이트.
- 실제 이슈 처리, PR 생성, 배포 성공을 패키지 생성만으로 보장하는 것.

## 2. 선택한 접근

**선별된 스킬 카탈로그와 고객별 조립**을 사용한다.

Superpowers 하나를 전체 골격으로 고정하는 방식은 빠르지만 고객 절차를 기존 방법론에 억지로 맞출 수 있다. 모든 스킬을 매번 새로 생성하는 방식은 자유롭지만 품질 편차와 유지보수 비용이 크다. 카탈로그 방식은 검증된 자산을 재사용하면서 고객별 절차를 별도로 유지한다.

세 프로젝트의 전체 워크플로우를 동시에 활성화하지 않는다. 인터뷰, TDD, 리뷰처럼 겹치는 역할에는 기본 구현 하나를 선택하고, 명시적인 입출력 계약으로 연결한다.

## 3. 사용자 흐름

1. 컨설턴트가 Copilot CLI에서 팩토리 스킬을 실행한다.
2. 고객 SDLC를 개괄하고 실제 병목 사례를 따라 인터뷰한다.
3. 고객 프로필을 정리하고 우선 워크플로우 하나를 추천한다.
4. 컨설턴트가 고객을 대신하여 선택과 워크플로우 명세를 확인한다.
5. 팩토리가 필요한 기본 스킬, 호환성 어댑터와 고객별 규칙을 조합한다.
6. 구조 검사와 외부 쓰기 없는 모의 실행을 수행한다.
7. 설치할 파일과 기존 파일 변경 내역을 제시한다.
8. 승인된 파일을 고객 저장소에 설치한다.
9. 고객 환경에서 인증 및 연동 사전 점검을 수행하고 결과를 기록한다.
10. 고객이 워크플로우를 시작하며, 필요한 승인과 수동 단계를 거쳐 실행한다.

팩토리 실행 환경에서 고객 환경의 인증·연결 상태를 확인했다고 추정하지 않는다. 두 환경이 같더라도 생성 검사와 실행 환경 사전 점검을 구분한다.

## 4. 구성요소와 계약

| 구성요소 | 책임 | 입력 | 출력 및 의존성 |
| --- | --- | --- | --- |
| 인터뷰 스킬 | SDLC와 병목, 용어, 제약을 확인 | 컨설턴트가 제공한 고객 답변 | 사실·가정·미확인을 구분한 고객 프로필 |
| 워크플로우 설계 단계 | 후보 비교, 우선 흐름 선택, 단계 계약 작성 | 고객 프로필, 카탈로그 기능 정보 | 사람이 승인한 워크플로우 명세 |
| 스킬 카탈로그 | 재사용 가능한 스킬의 계약과 출처 제공 | 검토한 상위 프로젝트와 적응본 | 고정 리비전, 의존성, 호환성 및 검증 상태 |
| 조립·생성 단계 | 명세에 맞는 스킬과 고객 규칙을 연결 | 승인된 명세, 카탈로그 | 전달 패키지와 출처 잠금 정보 |
| 검증 단계 | 구조와 모의 동작을 확인 | 전달 패키지, 샘플 입력과 모의 도구 응답 | 검사별 근거, 실패, 미확인 항목 |
| 설치·사전 점검 단계 | 변경 승인과 고객 환경 준비 확인 | 전달 패키지, 설치 대상 | 설치 결과, 인증·연결 점검 보고 |
| 생성된 워크플로우 진입 스킬 | 단계 전환, 승인, 인계 및 재개 안내 | 작업 입력, 명세, 로컬 실행 기록 | 단계 산출물, 상태, 다음 행동 |

각 구성요소는 명시된 산출물로 연결한다. 다음 단계가 대화 전체나 앞 단계의 숨은 추론을 알아야만 동작하도록 만들지 않는다.

## 5. 인터뷰와 중간 명세

### 인터뷰 방식

고정 설문 전체를 기계적으로 실행하지 않는다. SDLC 전체를 훑은 뒤 실제로 막혔던 업무 사례, 인계, 반복 작업과 승인 대기 시간을 따라 질문을 좁힌다. 한 번에 한 질문을 하며, 이미 확인된 정보를 반복해서 요구하지 않는다.

현행 절차와 목표 절차를 구분한다. 고객의 표현을 공통 용어로 정리하되, 고객 확인 없이 의미를 바꾸지 않는다. 답변에서 추론한 내용은 가정으로 표시한다.

후보 워크플로우는 병목 영향, 반복 빈도, 연동 준비도를 근거로 비교한다. 정밀해 보이는 임의의 점수 대신 추천 근거와 제약을 설명하고 컨설턴트가 하나를 확정한다.

### 고객 프로필

- SDLC 단계와 현재 업무 흐름.
- 고객 용어와 의미, 역할 및 승인 주체.
- 이슈 트래커, 저장소, CI, 문서 등 관련 시스템과 사용 방식.
- 병목 사례, 반복 빈도, 원하는 개선과 성공 기준.
- 접근 및 운영 제약, 현행 절차와 목표 절차.
- 확인된 사실, 가정, 미확인 사항 및 인터뷰 답변과의 연결.

### 워크플로우 명세

- 목표, 범위, 시작 조건, 작업 입력과 최종 완료 조건.
- 단계별 식별자, 책임, 입력·출력, 선행 조건과 다음 단계.
- 선택할 스킬과 필요한 도구 기능.
- 외부 상태 변경 여부, 승인 주체와 승인 지점.
- 실패, 승인 거절, 수동 인계, 중단 및 재개 경로.
- 지원되지 않는 연동과 그에 대한 수동 절차.
- 고객 요구사항과 단계·검증 항목의 대응 관계.

실행에 필수적인 미확인 정보는 승인 전에 해결하거나 명시적인 차단 조건으로 남긴다. 연결 정보를 추측해 실행 가능한 것처럼 생성하지 않는다.

## 6. 기본 스킬의 출처와 재사용

| 참고원 | 우선 활용할 패턴 |
| --- | --- |
| Superpowers | 인터뷰, 설계 승인, 계획, 실행 및 검증 게이트; TDD와 리뷰 규율 |
| gstack | 역할별 기획·엔지니어링·리뷰·QA; 단계 간 명시적 산출물 전달 |
| Matt Pocock Skills | 깊이 있는 인터뷰, 도메인 모델링, 이슈 트래커 설정, 작은 조합형 스킬 |

카탈로그는 각 항목에 다음 정보를 제공한다.

- 스킬 식별자, 담당 기능, 입력·출력 계약.
- 원본 저장소 URL, 원본 경로, 고정 커밋 리비전.
- 라이선스, 저작권 고지, 적응·변경 내용.
- 필요한 CLI, MCP 기능, 스크립트와 지원 자원.
- 외부 부작용, 승인 요구와 호출 제약.
- Copilot CLI 호환성 확인 상태와 검증 근거.

공개 프로젝트의 유명세를 호환성이나 동작 검증의 증거로 사용하지 않는다. Copilot CLI에서 검증되지 않은 항목은 실행용 기본 스킬로 승인하지 않는다. 사용자 호출 전용 스킬 등 원본의 호출 제약도 검토하며, 워크플로우에서 사용할 수 없는 경우 재사용 가능한 하위 스킬을 선택하거나 명시적으로 적응한다.

필요한 항목만 선별하고 원본 전체의 자동 시작 훅이나 갱신 기능을 함께 활성화하지 않는다. 고객별 규칙은 기본 스킬과 분리한다. 충돌은 숨겨진 우선순위나 조용한 덮어쓰기가 아니라 명세 검토 단계에서 해결한다.

세 저장소의 MIT 라이선스를 확인했다. 재사용·수정한 코드와 문서에는 해당 저작권·허가 고지를 유지한다. 고정 리비전으로 실제 도입할 때 라이선스 및 필요한 동반 파일을 다시 확인한다.

## 7. 전달 패키지와 설치

팩토리 자체의 프로젝트 스킬과 고객에게 전달하는 프로젝트 스킬은 **`.agents/skills/`**를 사용한다. `.github/skills/`에 중복 설치하지 않는다.

전달 패키지는 다음을 포함한다.

- `.agents/skills/` 아래 워크플로우 진입 스킬, 선택한 기본 스킬 및 고객별 스킬.
- 스킬이 참조하는 필요한 스크립트와 리소스.
- 승인된 워크플로우 명세와 실행에 필요한 고객 프로필 부분.
- 스킬 출처, 고정 리비전, 적응 내역 및 라이선스 고지.
- MCP·CLI 요구사항, 비밀값 없는 설정 예시와 인증 안내.
- 구조 검사 및 모의 실행 결과.
- 설치, 사전 점검, 실행, 수동 처리 및 재개 안내.

작업용 인터뷰 기록은 전달 패키지에서 제외한다. 고객이 확인한 실행에 필요한 정보만 포함하며, 비밀번호·토큰·인증 쿠키는 인터뷰 산출물이나 생성 파일에 저장하지 않는다.

설치 전에는 대상 파일, 추가·변경 내역과 충돌을 보여준다. 기존 파일을 승인 없이 덮어쓰지 않고, 고객의 다른 스킬이나 설정도 제거하지 않는다. 설정 예시는 고객이 실제 값을 입력하기 전에는 사용할 수 없음을 분명하게 표시한다.

## 8. 생성된 하네스의 실행

첫 버전의 하네스는 Copilot CLI가 읽는 스킬과 로컬 산출물로 동작한다. 별도의 서버, 스케줄러 또는 새로운 에이전트 엔진에 의존하지 않는다.

작업마다 실행 식별자를 부여하고 사용한 명세·패키지 버전, 단계 상태, 산출물 위치, 승인 및 실패 근거를 로컬에 기록한다. 실행 기록은 고객 환경에 남으며 팩토리로 자동 전송하지 않는다.

단계 상태는 최소한 대기, 진행 중, 승인 대기, 수동 처리 대기, 완료, 실패, 취소를 구분한다. 도구 실패나 미확인을 완료로 처리하지 않는다. 다음 단계는 명세의 선행 조건과 필요한 산출물이 확인된 뒤 진행한다.

재개 시 기록만 믿지 않고 실제 산출물과 외부 결과를 확인한다. 결과가 불명확한 댓글·브랜치·PR 생성 등은 자동 재시도하지 않는다. 기존 결과를 확인하거나 사람이 판단할 수 있도록 차단한다.

승인 거절은 후속 외부 쓰기를 중단한다. 지원되지 않는 연동은 수행할 사람, 필요한 입력, 기대 결과 및 재개 조건을 제시하고 수동 처리 대기로 남긴다.

행동 전 권한 부여와 산출물 승인은 구분한다. 요구사항·계획은 초안을 만든 뒤 사람이 해당 산출물을 승인해야 완료할 수 있다. 외부 쓰기와 수동 실행은 행동 전에 승인한다. 승인된 산출물을 다시 수정하려고 완료 단계를 조용히 재개하지 않는다.

실행 기록을 읽을 때는 이벤트 형식과 전이, 현재 상태와의 일관성을 확인한다. 현재 상태만 남거나 불명확한 외부 작업의 이벤트가 사라진 모순된 기록은 재시도의 근거가 될 수 없다.

스킬의 자연어 지침은 강제 실행이나 보안 경계가 아니다. 실제 접근 권한과 도구 허용은 Copilot CLI와 고객 시스템에서 제한해야 한다. 팩토리는 이 한계를 설치 안내와 검증 결과에 명시하며 전체 권한 허용을 설치의 전제로 삼지 않는다.

## 9. 검증과 인수 기준

### 구조 검증

스킬 형식, 로컬 참조, 스킬 의존성, 단계 입력·출력 연결, 승인·실패 경로, 출처·고정 리비전·라이선스 누락을 검사한다. 누락된 필수 항목은 명시적인 오류이며 준비 완료로 표시하지 않는다.

### 모의 실행

고객 워크플로우에 맞춘 가상 이슈와 모의 도구 응답을 사용한다. 실제 고객 시스템에 쓰지 않으며, 모의 도구 경로는 실제 쓰기 연동과 분리한다.

최소 시나리오는 정상 완료, 승인 거절, 연동 누락, 도구 실패, 중단 후 재개, 외부 쓰기 결과 불명확이다. 각 시나리오에서 기대 단계 상태, 산출물, 승인 대기 및 다음 행동을 확인한다. 외부 쓰기 결과가 불명확한 경우 중복 생성하지 않는지 확인한다.

구조 검사는 기계적 검증이고 스킬 모의 실행은 에이전트 동작 평가다. 두 결과를 합쳐 절대적인 실행 보장으로 해석하지 않는다. 요구사항과 관찰된 근거를 함께 기록한다.

### 고객 환경 사전 점검

필요한 CLI·MCP 가용성, 인증 상태와 필요한 읽기 접근을 고객 환경에서 확인한다. 도구가 제공하는 범위에서 권한 정보를 읽되, 쓰기 권한을 확인하기 위해 무승인 외부 변경을 하지 않는다. 확인할 수 없는 권한은 미확인으로 기록한다.

명세에서 필수로 지정한 도구나 읽기 접근 점검이 실패하면 해당 자동화 단계로 진행하지 않는다. 미리 승인한 수동 경로가 있을 때만 그 경로로 인계한다. 읽기 점검 통과를 쓰기 권한 확인으로 대체하지 않는다.

### 완료 표시

다음 결과를 분리하여 보고한다.

1. 패키지 생성 및 구조 검사 통과 여부.
2. 샘플 모의 실행 통과 여부와 관찰 근거.
3. 고객 환경 사전 점검의 통과·실패·미확인 항목.

전달물은 구조 검사와 모의 실행을 통과해야 한다. 고객 환경에서 확인하지 못한 사항은 별도의 준비 상태로 남긴다. 첫 실업무 실행과 실제 이슈 처리·PR 생성 성공은 이 인수 기준에 포함하지 않는다.

## 10. 오류 처리

- 필수 인터뷰 정보 누락: 해당 질문으로 돌아가거나 명시적 차단 조건으로 남긴다.
- 기본 스킬과 고객 규칙 충돌: 설명과 수정안을 제시하고 승인 전에 해결한다.
- 스킬 의존성 누락 또는 호환성 미검증: 자동 포함하지 않는다.
- 지원되지 않는 연동: 명시적 수동 단계로 설계하거나 해당 자동화가 불가능함을 표시한다.
- 검증 실패: 실패 항목과 영향을 보고하고 생성 완료와 실행 준비 완료를 혼동하지 않는다.
- 기존 설치 파일 충돌: 변경 내역에 대한 승인 전에는 쓰지 않는다.
- 인증 실패: 비밀값을 요청·기록하지 않고 고객 측 인증 안내를 제공한다.
- 도구 실행 결과 불명확: 후속 변경을 중단하고 결과 확인 또는 사람의 판단을 요구한다.
